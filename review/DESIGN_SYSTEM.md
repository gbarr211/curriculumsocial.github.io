# Curriculum Social — consistent product experience

Confirmed direction, 2026-10-10: all pages should look consistent, easy and attractive; student access can be more playful. Prioritize finding families, creating/joining events and pods, applications, and pod/class learning votes.

The movement's warm paper, forest ink, lime and clay palette now defines `css/community.css`. Serif page titles pair with readable sans-serif controls. Shared rounded cards, form fields, pill buttons, clear active navigation, visible focus, roomy touch targets and responsive grids carry across account and community pages. Student space adds sunny/lilac accents within the same components, with short offline adventures and no streak/pressure mechanism. This direction remains reviewable; no user preference for a different palette has been inferred.

Shared CSS and navigation entry points are added to every existing root HTML page (31 source pages), preserving existing event targets and unrelated page logic. The older inline styles are overridden by common tokens/components. This is a styling foundation, not a claim that every legacy layout or placeholder is fully redesigned or functional. Existing public main is unchanged.

The private preview adds a coherent seven-screen community experience: dashboard, family matching, events, pods, learning votes, applications and student space. It retains and restyles account signup/login/profile previews. Family search supports area/approach and empty/reset states; connection requests are drafts. Events support details, joining/leaving, waitlists and creation with validated capacity. Pods support proposals, join-interest drafts and group-specific learning views. Votes are replaceable preferences scoped to a pod or class; new groups show an empty planning state. Applications require a concrete offer and availability. Student choices route to a sample class vote and support reversible offline-adventure markers.

All new community data is synthetic and lives only in memory until reload. No network calls, browser storage, Firebase users/records, messages, bookings, permissions, teacher verification or real curriculum approvals are produced. Account preview services remain simulated. Production Firestore remains default-deny. These are tested product interactions, not a validated engagement outcome or live service.

Actual checks and publication evidence are indexed in the existing project audit and daily build record. Managed browser layout/native dialog/assistive-technology checks remain pending because the required control-browser capability is unavailable. Before live release: replace synthetic services with approved, ownership-tested persistence; resolve privacy/retention; validate permission rules, real sessions, mobile layouts, native modal keyboard/focus behavior and error recovery. Legacy pages need individual content/layout checks, including unsupported historical marketing claims, before they are released under the shared style.
